# 文章写作流水线（write-article）

你的角色是**编排者**：素材收集、结构规划、质检、防编造是你擅长的；**文笔和语感交给 kimi**（`gcli api --provider kimi --model kimi-k2`，一次 HTTP 调用，秒级）。这个分工经过 2026-08-29 双稿实测验证——kimi 用对了风格指令和事实底座能写出平台立得住的稿子，但在缺素材时会编造一手经历（实测稿 A 出现两处），所以**事实纪律由你机器层强制，不由起草模型自律**。

## 流水线总览

```
① 选题质检(HKR) → ② 素材事实底座(material.md) → ③ kimi 起草(gcli api)
→ ④ 四层质检(L1脚本/L2风格/L3事实溯源/L4活人感互评) → ⑤ 人终审(+衔接 /oss-preflight)
```

对外发布物最终走 oss-ops L2 审批流（见 `martin/oss-ops.md` §2），本流水线产出的是**待审批草稿**。

## ① 选题质检（HKR）

动笔前三问，≥2 项「是」才值得写，否则先和用户对选题方向：
- **H (Happy)**：有趣、有悬念吗？标题能让人想点开吗？
- **K (Knowledge)**：读者看完能带走新东西吗（信息/方法/避坑）？
- **R (Resonance)**：能戳中「对对对我也是」吗？

信息不够就问用户：「你想讲哪几个点？有没有自己真实的经历想放进去？有没有特别想吐槽的？」——一手经历只能从用户嘴里来，问出来的是真的，编出来的是事故。

## ①.5 产品深潜（多 subagent 并行，2026-08-31 用户拍板新增）

**写文章的人必须先真懂产品。** 懂 = 能回答「它有哪些好用的能力、各是什么手感、为什么这样做、用户真实要什么」。不靠 README 印象，派四个 subagent 并行深潜（Agent 工具），产出直接喂 ② 素材底座：

| agent | 任务 | 产出→底座层 |
|---|---|---|
| **功能盘点** | 从代码+README+路由全量枚举功能（含 UI 里不显眼的能力），每条带 `file:line` 证据 | 事实层（功能清单） |
| **体验实测** | 本地跑起来走核心动线+试边界（如 ai-todo 的 AUTH_DEV_BYPASS+seed-demo），记录惊喜点与摩擦点 | 产品理解层 |
| **设计决策** | codebase harvest：schema 注释/exit code/测试文件名/git log 挖设计 why | 设计决策层 |
| **诉求采集** | opencli 社区搜索真实用户原话（小红书/Reddit/V2EX/竞品 issues/HN），≥3 条带源 | 诉求证据层 |
| **使用痕迹挖掘** | 挖**作者自己运行数据里「日用而不自知」的用法**：hermes sessions FTS5 搜任务相关会话（按渠道/语音筛）、产品自身 DB 的使用痕迹（如 voice_raw_text/创建渠道/频次）、cron 投递史、gateway 日志 | 叙事层（真实使用场景） |

纪律：五路并行放一条消息里同发；功能盘点/设计决策是只读快 agent（用 Explore）；体验实测要真跑环境（已有脚本复用，如 `apps/web/scripts/seed-demo.mjs`）；使用痕迹挖掘注意隐私——只浮出聚合统计和候选片段，具体内容用户终审才进文章；**深潜未完成 = 产品理解层空缺 = 不起草**。08-31 实证教训：编排者对产品的认知是「读出来的不是摸出来的」，写出的文章只有功能清单没有手感；同日第二实证：用户「微信语音 CRUD 任务」这个核心日常场景自己不会主动提（日用而不自知）——**最强的痛点素材在运行数据里，不在用户嘴里**。

## ①.7 视角切入（angle 决策点，2026-08-31 用户拍板新增）

**素材就位≠知道从哪写。** 同一池素材可以切出完全不同的文章，切入角决定打开率和共鸣度。这是独立决策点，不隐含在起草里。

**输入**：产品深潜产物（①.5）+ 诉求证据 + 目标平台。
**方法**：kimi 生成 5-6 个候选角度（每个 = 标题候选 + 立意一句 + 开头第一句 + 点开理由 + 主打素材点），Claude 按四准则打分排序：

1. **共鸣强度**：诉求证据里有没有真实用户原话撑这个角度（有源 > 脑补）
2. **差异化**：同角度别人写过没有——写过就换，或给出我们独有的深度（深潜产物是差异化的来源）
3. **证据厚度**：素材能不能撑起这个角度的每一段（撑不起的角度是空中楼阁）
4. **平台匹配**：内容消费社区读者视角、发布社区宣告体（viewpoint-laws §四）

**产出**：排序表 + 推荐，用户挑（实时路会话内快速定）。**一鱼多吃**：同素材池可按「角度×平台」矩阵出多篇，但同平台同角度不重复发。08-31 教训：ai-todo 首稿角度（如何让 Claude Code 记住长期任务）用户直觉「不一定打到用户」——角度没被显式决策过，是被默认的。

## ② 素材底座（事实层防编造 + 叙事层防教程体）

写 `material.md`（模板见 `references/material-template.md`），规则：

1. **只放真实事实**：gh/git 查到的数据、真实发生的事件、实测命令的输出、用户亲口说的经历。每条标注来源（`gh repo view` / 「用户 08-29 口述」 / commit hash）。
2. **一手经历必须标注** `[待补：用户填]`：为什么做这个东西、当时什么感受、具体某次使用场景——起草模型遇到这些位置就留白，终审时让用户填。**宁可整段留白，不可代编**。实测证据：kimi 在素材不足时会自己编「我在 Claude Code 里顺手说了一句话它真的写进去了」这种以假乱真的一手经历，读者无法分辨，作者翻车。
3. 素材充足的标准：核心卖点有真实例子、有真实数据、有真实链接。缺哪个就去收集哪个（gh api / 日报 metrics / 跑一遍命令），收集不到就留白。
4. **配图一律过图床**：本地截图/GIF 先 `tunnel img <path>` 拿公网 URL（stdout `✓ URL`，取第二列）再写进 markdown——各平台正文直接贴本地路径会挂。图床已验收（2026-08-29）：content-type 自动正确、`cache-control: immutable` 一年缓存、CORS 全开、657KB GIF 无压力、`tunnel img ls` 可查、`tunnel img rm <id>` 可删（rm 后 404 已验证）。**边界**：文章/社交内容用图床 URL；GitHub README 内的图用仓内相对路径（跟着 repo 走，fork 不断链）。
5. **叙事层必填（2026-08-31 升级，防教程体的根）**：时间线（起点→第一个动作→转折/意外→现在→情绪锚点）+ 踩坑记录（现象→为什么难→怎么解）。**没有叙事层的素材底座不准进 ③**——只有事实层时模型只能按「合理结构」编大纲体，08-31 掘金稿被毙的根因就在这。采集协议：用户在场就口述（三五句起步，「然后呢？」追问）；不在场就从历史会话/issue/commit 挖；都挖不到就标缺口、宁可延期不起草。

## ③ kimi 起草

组装 prompt，**四件套按序拼接**（2026-08-31 升级）：

```
① 叙事风格核心全文（references/style-narrative-core.md，所有中文长文必带）
② 平台惯例（references/style-zh-v2ex.md 等，只管渠道习惯：篇幅/emoji/链接放置）
③ 作者风格范本（references/exemplars/，用户本人文章，few-shot——比任何平台语料权威）
④ 素材底座（material.md 全文，含叙事层）
```

从 stdin 喂给 kimi：

```bash
export https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890
cat prompt.md | gcli api --provider kimi --model kimi-k2 -p - > draft.md
```

| 平台 | 平台惯例 | 说明 |
|---|---|---|
| V2EX 分享创造 / 掘金 | `references/style-zh-v2ex.md` | 掘金长文加叙事核心；V2EX 发布档短帖惯例为主 |
| dev.to / 英文 | `references/style-en-devto.md` | 英文轨；叙事核心原则适用但签名词不适用 |

**起草前必过 [`references/viewpoint-laws.md`](references/viewpoint-laws.md)（视角转换定律）**：同场景下发布者视角与读者视角差 100 倍（实证 2026-08-30）。核心：标题=读者痛点/目标而非产品名；开头降姿态（转述/亲测/踩坑）；产品藏手段位；诚实折扣必配；为收藏设计。**渠道语境例外**：发布类社区（V2EX 分享创造/dev.to showdev/Show HN）接受宣告体；内容消费社区（小红书/B站/知乎/掘金）必须读者视角。

prompt 末尾固定要求：「只用素材里的真实事实，叙事弧线只走素材叙事层的时间线，宁可留白也不要编造细节。直接输出标题+正文，不要解释。」

改稿往返：把修改意见 + 原稿一起再调一次 kimi（它没有会话记忆，每次都是全量上下文）。

## ④ 四层质检（顺序执行，层层拦截）

**L1 硬规则扫描（脚本，机器强制）**：
```bash
python3 scripts/scan.py draft.md
```
禁词（说白了/这意味着/本质上/赋能…）、英文 AI 指纹词（delve/seamless/game-changing…）、结构套话（在当今…的时代/让我们来看看）零容忍，命中即改。

**L2 风格一致性**：对照所用风格规范逐项过（开头方式/篇幅/结构轻重/语气/链接放置/互动钩）。读起来「像报告」的段落重点改。

**L3 事实溯源**：逐断言核对 material.md——草稿里每个事实（数字/功能/链接/经历）都必须能溯源到素材条目。**溯源不到 = 编造 = 删或留白**。这一步是你（Claude）做，不用模型自查——实测证明起草模型对自己的编造没有自我意识。

**L4 活人感互评（独立视角）**：再调一次 kimi，但**不带任何起草上下文**，只给成品：
```
【你是审稿人，不是读者——禁止讨论文章观点、禁止延伸补充】
这是一篇准备发在 <平台> 的帖子。以一个常年混这个社区的读者身份读一遍，回答：
1) 哪一段让你觉得"这段是 AI 写的"？具体到句子 2) 哪一段最像活人写的，为什么
3) 你会回帖吗，想回什么。只说真话，这稿子毙掉对你没损失。
4) 【成稿 HKR 复验】读完后你能带走什么具体的东西（方法/判断/可抄的配置）？
   哪一段让你有"对对对我也是"的同感？答不上来就说没有——这是吸引力判据。
```
起草模型不能给自己打分（写作者盲区），fresh-context 互评 + 你的 L3 是双保险，人终审是最后一道。**08-31 实证：不声明「审稿人不是读者」，kimi 会被好内容吸引去讨论观点而忘记挑毛病。**

## ④.5 平台分级质量门槛（硬门槛，2026-08-31 事故教训）

**扫描干净 + 事实真实 = 底线不是质量线。** 一篇稿「没违规」不等于「值得发」。起草完先按平台档对下表，不达标直接退 ③ 重起，不进 ⑤ 浪费用户终审时间：

| 档 | 平台 | 硬门槛 |
|---|---|---|
| **深度档** | 掘金 / 少数派 / dev.to | 正文 ≥1500 字（不含代码块）+ **≥3 张实拍配图**（截图/录屏/GIF，过图床）+ 读者视角手法（标题=痛点/目标，正文 how-to 或踩坑叙事，产品藏手段位） |
| **轻量档** | 小红书 / 即刻 / 微博 | 300-800 字 + ≥1 张图 + 视角定律照常 |
| **发布档** | V2EX 分享创造 / Show HN / release notes | 篇幅灵活，但必读该站 style 规范；V2EX 见 style-zh-v2ex.md |

事故教训（08-31 掘金稿被用户毙）：标题换了视角定律但正文还是宣告体改装；550 字纯文字零图发深度平台——「风格干净」通过了质检，「质量够格」没人验收。**改版核心：质量判据（值不值得收藏/有没有不可替代洞见/配图是否到位）必须在进终审前自评，写进 draft 头注释。**

## ⑤ 人终审

向用户呈现：草稿 + L4 互评摘录 + `[待补]` 位置清单。用户填一手经历、拍板定稿后：
- 对外发布 → 走 `/oss-preflight` + oss-ops L2 审批
- 留档 → `write-article-workspace/drafts/`，好稿回填 corpus 作 few-shot（用户明确认可后）

## 迭代纪律

- 每次发布后的真实数据（回复/阅读/star 归因）回写 `write-article-workspace/`，风格规范据实修订——**规范是语料的提炼，语料是社区的反馈，不是一次性的**
- 新平台接入 = 收该平台高赞文 3-5 篇进 corpus + 提炼规律成新 style-*.md，不拍脑袋写规范
