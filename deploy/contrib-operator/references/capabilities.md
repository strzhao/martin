## 4. 能力用法

### 4.1 kanban 工具面（本板）

- survey：`kanban list/show`（triage 列=收件箱最老优先；scheduled 列=到期 watch；done 近 48h=守候）；`sqlite3 file:…?mode=ro` 只读查事件
- 分诊产出：出手=起 `[q]` 深研卡或直接走 4.3；观察=建 `[watch]` 卡；**放行=直接 archive**（operator 是 cron agent 外部 actor，看板全权——下方「派单 worker 无跨卡终态权」各条仅对 **specialist worker** 适用，operator 不受此限）。
- **派单 worker 无跨卡终态权（实测，踩过两班 90 轮超时）**：`kanban_complete/block(task_id=<他人卡>)` 一律被 kernel 拒（`worker is scoped to task <本卡>; refusing to mutate …`）。可用通道：跨卡 `kanban_comment` ✅ / 跨卡 `kanban_show` ✅ / 跨卡终态 ❌。→ 分诊放行的落法是**跨卡 comment**，首行写机器可读行 `triage-verdict: pass|act | issue #N | space=K（占坑 PR 实查值）`，逐卡落完再在台账文件汇总；triage 列的自清依赖编排层批量释放或人工，不要反复重试 complete（重试=白烧轮次预算）。
- **`[watch]` 无 schedule 手段（worker 侧）**：`kanban_create` 只收 `initial_status ∈ {running, blocked}`，而 blocked 会被 kernel promote 成 `ready` → 到期日前被提前派发（要么白跑一轮，要么被 worker complete 而丢掉观察）。建 [watch] 卡时必须在 body 首段写明「到期日前勿派发」并显式告知人工置 scheduled。**缺口处置成稿（09-13 shift-18，可直接复用，勿每班重写）**：`contrib-data/heartbeat-clamp-fix-20260913.{md,patch,sh}` = 一次性 schedule 迁移（方案 A）/ 应用补丁（方案 B，推荐）二选一，补丁三处修正已过 `bash -n` + `git apply --check`；**已于 shift-19 以方案 B 落地（提交 `aae37c1`，详见下方「钳夹新状态」条），勿再重复执行。**基线：blocked 带到期行的 watch 卡 4 张（`t_1621971d` 09-15 / `t_db200d54` 09-16 / `t_03bc12f0` 09-16 / `t_50ff94bb` 09-17）+ scheduled 2 张（`t_26d4c387` 09-18 / `t_19c1f214` 09-20）；`kind='unblocked'` 事件史 = 0（钳夹从未成功唤醒过任何卡，故 operator 班次巡检恒为唯一可靠 actor）。**重复写「请编排层置 scheduled」= 噪声**（前四班已四犯）：正解 = 卡面成稿 + `block(kind=capability)` + 每班巡检兜底。
- **operator（cron agent）可直接置 scheduled（09-14 shift-39 实测 rc=0，板库实读 status=scheduled）**：`hermes kanban --board contrib schedule <id> "<reason>"`——**没有 `--due` 参数**（写了报 `unrecognized arguments`），到期日只在卡内评论的机器行里表达。⚠ **位置参数 reason 会被 append 成一条评论** ⇒ reason 文本里**不得出现带冒号的到期 token**（否则巡检器把它后面 10 字符当日期窗口读）；写「到期日见评论机器行」这类**无冒号**措辞即可。建 [watch] 的标准三步：建卡（`initial_status=blocked`，body 首段写「到期日前勿派发」）→ 补一条**只含一次**到期机器行的评论 → `schedule` 置 scheduled 并实读板库自证。**再布防的唯一 token = `watch-due:`（10-06 实证）**：当班复检完成后续期时写**新一条**评论，行首恰为 `watch-due: <YYYY-MM-DD>`——自造 token（实例：`watch-rearm:`，钳夹不识别 → 新窗口从未生效）或纯散文 verdict（实例：needs_input 判词无机器行 → 「复检已完成」不在钳夹读取域）都会留下旧窗口 → 次日同 tick 假唤醒白烧 worker run（t_4933c284/t_75ff3028 双实证，patrol log `woke … due=2026-10-06` 二连）。**判 needs_input（等用户）的卡无日期型复查需求 → 仍须补一条远期压制窗口**（如 +30 天），否则旧窗口按月循环触发。钳夹无 per-comment latest 语义、读的就是所写之物 ⇒ 数据面权威行是唯一修复位，SQL 侧改 latest 判定=已由本条覆盖（KISS，不改代码）。**⚠ 「（watch-due）」括注形 = 第三种静默失效（10-13 01:0x 实证，单班 5 例）**：`watch-due` 行共存）。**worker 侧续窗系统性踩坑（本班分布）**：t_975726cd 散文括注形、t_b7dc76f8/t_ccc8610e 建卡只写卡体散文零机器行、t_c2df2cbb 窗口只写 schedule reason——worker/建卡路径把「写窗口」理解成散文描述，机器行纪律只在 operator 手里（**10-25 08:1x 修正：operator 也会犯——operator 建 watch 卡时先写了一条带日期无 token 的散文评论「守候窗口记录：本卡到期复查日为…」，靠写后自证（python sqlite3 复读 task_comments 跑钳夹同式 SQL）抓回补了第二条真机器行；教训 = 日期与 token 必须同一条评论、行首严格 `watch-due: YYYY-MM-DD`，写后自证必须跑 `body like '%watch-due:%'` 的钳夹同式查询而不是肉眼看评论内容**）。⇒ **每班巡检必查「scheduled+blocked 无合法形状机器行」集合**（一条 SQL：`status in ('scheduled','blocked')` 且 `not exists comment body like '%watch-due:%'`），发现即 operator 补行归位； worker 收口 [watch] 卡复检时若已 complete（run 2065 实证：schedule 对 done 卡三连拒绝+「终态窗口」心跳耗轮）⇒ 守候链丢失，**create-only 重建续期卡**（idempotency_key 带 v2 防重）。**⚠ [watch] 卡禁用 kanban_request_review（10-19 t_b2c90b52 实证）**：request_review 把卡置 review mismatch），worker 无法自纠回驻留。正解=**create-only 续期卡（parents 挂本卡，父母 done 前不派发）+ kanban_complete 放行**（t_56f79bb3→t_b2c90b52 先例形态），卡上留 reviewer「无改动批准」指引；review 批准瞬间续期卡自动就绪，窗口有余量时零伤害。**stale 判据以作者时钟计（10-19 实证）**：alt-glitch 等机器人标签治理（label swap，issue+PR 同秒 updatedAt 联动）会推高 PR updatedAt 而非作者动作——timeline 全事件归因（作者名下有无 edited/comment/commit/review）后按作者最后真实动作计 stale，bot 事件一律不计；机械复述「updatedAt 陈旧 N 天」会把 16.1d 实际停滞误判成 1.9d。**零外流复验按分支名精确探（11-05 实证）**：让路件守候复验的 `git ls-remote fork` 若用宽口径 grep（issue 号|机制词如 transform|suppress）会把无关同名面旧分支误判成外流（本班命中 cron 面两支 `*-suppression` ⇒ 假阳性「!! 有外流」）；正解 = 精确探件分支名（`grep -i 'forge/<id>'`）零命中才证毕，宽口径命中先查归属再定性。
- CLI 有 `hermes kanban schedule`，但 worker 上下文被 write fence 硬拒（原文 `kanban: delegate_task child contexts cannot mutate Kanban tasks via the CLI`；源码 `hermes_cli/kanban.py:214-226` denied 集含 `schedule` + `kanban_db.py:121-136` `_assert_not_delegated_child_mutation`）——**别在这条路上反复试**，「置 scheduled」环节恒归编排层。
- **`scheduled` 到点不会自动唤醒（源码实证，09-13 修正）**：`schedule_task` 只是把 status 改 `scheduled` 并把到期说明写进 reason（`kanban_db.py` 3767-3790，docstring 原话「not dispatchable until unblock_task re-gates it」）；dispatcher 每 tick 只枚举 `ready`/`review`（`kanban_db_dispatch.py` `_dispatch_once_locked` → `_lane_rows(conn,"ready")`，`_lane_rows` 按单一 status 过滤），**没有任何按时间 promote `scheduled` 的代码**。全机也无脚本/cron 做「按日期 unblock」：run-watch.sh / contrib-sweep.sh / 全部 launchd agents / default cron jobs 实查皆无。⇒ [watch] 的责任链 = **到期日由人工或编排层（`default`）unblock**，不是「到点自己醒」。
- **钳夹解析契约（写机器行前必看，09-13 15:0x 实读源码）**：`substr(trim(replace(body,char(13),'')), instr(...,'watch-due:')+11, 10) <= date('now','localtime')` ⇒ token `watch-due:` 后**恰好一个空格**再写 `YYYY-MM-DD`（`+11` 跳过 token 尾+那一个空格）。两个空格/无空格都会取错 10 字符窗口：多一个空格则窗口以空格开头（恒小于日期 → **立即误判到期**），少一个空格则末位截掉数字。每班核对一条 SQL：`sqlite3 "file:<DB>?immutable=1" "select task_id||' :: '||substr(body,instr(body,'watch-due:')+11,10) from task_comments where body like '%watch-due:%';"`。散文里复述该 token 同样危险（窗口取到中文/引号 ⇒ 字节序大于数字 → 恒判未到期，反向漏唤醒）。另：`mode=ro` **不是必失败**——09-13 15:06 实测 dispatcher 活跃（`-wal`/`-shm` 在位）时 rc=0 正常返回，静止时（sidecar 不存在）rc=14 ⇒ 属**竞态型静默失败**，故每班自查是唯一可靠兜底。
  - **静止态复现法（09-13 实测，验证任何钳夹改动都用这招，别拿生效脚本试）**：`sqlite3 "file:<DB>?immutable=1" ".backup '/tmp/x.db'"` 得到无 sidecar 的库副本（文件头 18/19 字节仍 `02 02` = WAL）→ 该副本上 `?mode=ro` **必** rc=14 `unable to open database file`、`?immutable=1` rc=0、`?mode=rw` 亦可 ⇒ 改前先用副本跑通，再动生效脚本。
  - **过滤放宽必须同加日期形状守卫**：把 `t.status='scheduled'` 放宽到 `in ('scheduled','blocked')` 时，必须加 `due glob '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'` —— naive 放宽会**当天**误唤醒散文里复述过 token 的卡（09-13 实测 `t_8bc51715`：窗口 = `' 行请编排层 unb'`，首字符空格 0x20 < 数字 0x32 ⇒ 恒判「已到期」）。`?mode=ro`→`?immutable=1` 时同时把 `2>/dev/null || true` 换成 rc 捕获 + 落日志，否则修了读取仍留静默。
- **每班必查 scheduled 列（到期巡检）**：读卡标题与 scheduled 事件 reason 里的复查日，与今天比对。到期/过期 → 跨卡 comment 写机器可读行 `watch-due: <YYYY-MM-DD> | status=<已/未到期>` 提请编排层 unblock（worker 无跨卡终态权，也 unblock 不了别人）；未到期 + `contrib-data/watch-*.json` 判据在位 = 健康，本班不动、零成本跳过。**巡检取数一律复用 patrol 的 READ_SQL 口径（跨评论 MAX 合法窗口），禁手写按行 regex**：按行 split 含换行的评论 body 会漏读 worker 续期机器行 → 假逾期警报（10-06 14:0x 实证：临时脚本报 3 张 blocked 卡逾期，patrol READ_SQL 实测 MAX=10-12/10-12/10-07 全未到期；patrol 零日志=零到期非读断，手动复跑 rc=0 自证）。**班内探针的窗口读数落点 = `task_comments` 表，不是 `tasks.body`**（到期机器行按钳夹契约写进评论，body 里恒无——s110-hygiene 读 body 报 `none`，历班「09-18」是转抄非实测；s111 改读评论表后实测口径吻合。查法：`select body from task_comments where task_id='<id>' and body like '%watch-due:%'` + 正则 `watch-due:\s*(\d{4}-\d{2}-\d{2})`）。
  - **⚠ 到期卡会被两个 actor 同时捞：班次动手前先读该卡的 `unblocked → claimed → spawned` 事件链（09-15 实证）**：巡检器的唤醒方式 = `kanban unblock`，卡随即回 `ready`，**dispatcher 会在秒级认领并 spawn 一个 worker run**（09-15 实测：00:02:09 unblock → 00:02:24 claimed+spawned，run 286）⇒ 同一张到期卡上「班次复检」与「worker 复检」并行发生（当天两方各做一遍全量复检，结论一度相左，worker 随后自纠归位）。纪律：**班次先读 `task_events`，见 `spawned` 即判「worker 已持有」⇒ 让 worker 执行复检，班次只做核对与归位**；两方结论冲突时以 **operation 层裁定**为准，且**第二个落笔者必须归位数据载体**（把 `contrib-data/watch-<题>.json` 的 `status` / `superseded_by` 改成与看板真相一致，否则载体与看板互相矛盾）。机制层若要消除重复，方向 = 「巡检器 unblock 时给卡加短 TTL 的 operator/worker 二选一标记」，**本域未做**（Q4 剃刀：重复劳动有界 —— 一个 worker run、零 budget、零对外动作，净增零件是负收益）。
  - **板库路径口径（shift-25 实查固定，2026-09-14）**：contrib 板真身 = `~/.hermes/kanban/boards/contrib/kanban.db`（`hermes kanban --board contrib` 的实际落点；board 库格式为 WAL）。形近陷阱（本班逐一实查）：`~/.hermes/kanban.db` = **default 板**（129 条）；`~/.hermes/kanban-contrib.db` / `kanban.contrib.db` / `profiles/contrib/kanban.db` **均无 tasks 表**；`~/.hermes/kanban_ro_copy.db` = 一次性静态副本（74 条、09-11 至今不变，勿用）。只读取数口径（10-23 修正）：**读「近期写入」用 `?mode=ro`（WAL-aware），读「静止历史」才轮到 `?immutable=1`**——immutable=1 只读主库文件、忽略 WAL，dispatcher 活跃窗（sidecar 在位）会静默漏掉最近写入（见 §4.5 10-23 探针认知条）。

### 4.3.1 抢跑道：先占坑 PR + 并行深检（用户拍板成原则）

**背景（定量复盘结论）**：被抢时间差实测中位数 **10 分钟**、P25=5 分钟、约 73% 在 15 分钟内；我方岗哨 20 分钟一班 + 出手链路（验证→过闸→forge init）1-2 小时 ⇒ **速度战结构性赢不了，也不去竞**。但逐条核对被抢案例：绝大多数为作者自配对/我方本就 pass 的零契合面，**真错过（契合达标+想出手+被抢）极少**——真正的损耗是「契合 3 + 独家证据现成」的热题因深检串行而被拖慢。抢跑道只为覆盖这类我们能赢的出手，不与 farm 比手速。

**触发条件（三条同时成立才可走抢跑道，缺一不可）**：
1. **契合 3**（核心链路咬伤）+ **独家证据现成**——本机现场在案（报错日志/复现命令/受影响 wire 实证），不需要新取证；
2. 当班配对探双空（单号 0 + xref 空，且不在维护者协调令/分配行内——查 §3.6 前置）；
3. issue 开出 ≤30 分钟（热点新鲜度窗口；超窗走常规深检流，抢坑无意义）。

**流程（与常规流的差异点）**：
1. **先占坑**：gap 逐字实锤（对 origin/main 指到行）→ 最小可信修复（单关注点 + base 证红 + 1-2 条不变量测试，§4.3 自检 ①③④ 快速过）→ **draft PR 先开**（首行声明 `Draft — hardening in progress, will remove draft flag after full verification`）⇒ 占坑时刻从 1-2h 压到 20-30 分钟；
2. **并行深检不跳过**：forge 流程照跑（§4.3 全套自检 ①-⑥ + RED/GREEN 补齐 + 兄弟调用点排查）；
3. **深检出问题自己修**：发现面更大/处方错误/测试不充分 → **自己修好再转 ready**，不许带着已知缺陷移除 draft 标记——draft → ready 的转换 = 深检全绿的自证时刻；
4. **深检后放弃的退出纪律**：若深检推翻出手前提（不是我们以为的那个 bug / 面被上游修复 / 协调令浮出）→ **主动关闭自己的 PR** + issue 下一条诚实说明（「withdrawn after deeper verification, found <原因>」）——撤得干净是姿态红线的一部分，占坑不兑现比不占更伤品牌；
5. **台账与复盘**：抢跑道出手逐条落 journal（触发三条件逐项核验记录 + 占坑→ready/关闭 的端到端时长）；每 10 次抢跑道出手做一次复盘（胜率/自修率/撤回率），胜率 <50% 或撤回率 >30% ⇒ 机制回滚评估。

**边界**：
- 协调令/分配行/维护者已点名分装的题**永不抢跑道**（速度不豁免协调红线）；
- 独家证据不现成的题**不进抢跑道**（占坑 PR 带错误处方比晚到更伤——深检兜底是修正自己的小错，不是补侦察的大洞）；
- draft PR 的 body 也要过 §3.6 草稿质量法（占坑≠可以糙）；
- 本跑道不改变 §0 铁律 5（agent 起草，链落笔）——push 与开 PR 仍走既定外发通道。

**上游 PR 配额（10-18 实证定谳，取代旧「仓库级权限收紧」误诊）**：上游对无写权限账号限 **5 个 open PR，draft 也计数**（GitHub 2026-10-08 起的仓库配置；创建被拒报 limit 错误，属配额用尽，非权限故障/账号问题——此前被拒错误码伪装成 404 致误诊）。10-18 以「静默关 48 留 4 → PR #141151 即时挂出」实证闭环。open PR 是稀缺资源：**造货终态默认 branch-only 入库**（锚 issue + review offer 带 fork sha 都不占配额），PR 只为活跃收敛窗开；槽位满时自己权衡关谁——真人互动 × mergeable 优先留；关 PR 不销毁库存（分支留 fork，可被 sha 直取或重挂；重开也占槽）；实时槽位 `gh pr list --author strzhao --state open` 现查，不建账本。抢跑道步骤 1 的 draft PR 先开同样占槽，走不走按当下配额自裁。draft 车质量要求照旧上调（Fixes 锚/mergeable/干净 rebase）以最大化被收编概率（车主路径=被维护者收编，先例：#86622/#109758 fork sha 直取、署名落袋）。
