| 不修会怎样 | 损失 = 每周多读一本账、多跑一个 `verify`、多维护一份字段契约（**负收益**，不建才是收益） |
| **verdict** | **`already-covered`**（整件删除，只留一条文字约定：修复的提交说明必须写 why） |

**拦截发生在哪一步**：**Q2，三条只读命令，30 秒**。三问（Q2/Q3/Q4）结论一致，互相印证。

**但真正的方法论结论在别处**：v1 的设计里**没有 Q2 这个栏目**——它的流程是「设计 → 实施」，没有任何一步要求先问「这件事 git/看板/钳夹/知识层是不是已经答了」。**所以拦住它的不是「更聪明的人」，是把 Q2 变成卡上必答栏**。这正好复述了用户的根因判断（缺的是指导，不是机制）。

### 2.3 能不能事前拦截？逐问判定（诚实版）

| 问 | 对 v1 的账本 | 对 run-watch 的膨胀 |
|---|---|---|
| **Q2「已有基建 sweep」**（v3 形：逐项点名 + 命令 + 输出要点） | **能拦，三条命令结案** | **不能单独拦** ❌。逐次看，每一段都是**新能力**（T3「radar/mail 判断卡化」没有任何既有基建覆盖），逐项点名只会逐项通过。**Q2 的判据是「是否已被答了」，不是「是否该长大」** |
| **Q2 +「同形已有几件」**（v3.1 新增那一行） | 同样能拦（无需这行） | **能拦，拦在第 2 件** ✅。T3–T6 的共同 shape =「把某阶段的判断卡化到 kanban」——第 2 件出现时就该停手出**一个通用卡化抽象**，而不是 4 段各写各的。按实查节奏（T1 09-09 135 行 → T3 同日 +322 行 → T4 09-09 → T5 09-09 → T6 09-10），**拦截窗口 = 同日内**，不需要等周议程 |
| **Q3 KISS 阶梯** | 能拦（三级全否 ⇒ 落到「新建」时暴露） | **不能单独拦** ❌。每段单独看，「能删吗/能配置吗/能改一行吗」的答案都是「不行，因为这是新能力」⇒ 每段都合法落地 |
| **Q4 剃刀（净零件计数）** | 能拦（净 5 ⇒ 「零新增不行」答不了） | **不能单独拦，但它是唯一的「记账器」** ⚠。逐件都答得出「零新增不行」；可是**数字会累积**：+807/−107、删除/新增比 0.13、单文件 700 行。**没有这个数，膨胀是不可见的**（v1 §4.1 的「无收敛压力」诊断只有定性描述，没有逐件数字） |
| **「不修会怎样」栏** | 对账本：不建的收益（负收益）一眼可见 ⇒ 支持删除 | 对 run-watch：每一段都有「不写这段就没人管某阶段」的正面论证 ⇒ **它天然偏向「修」**，拦不住膨胀 |

**结论（这一节的产出）**：

1. **对 v1 的账本**：Q2 一把就够（三命令、30 秒），且三问互相印证。**拦截力来自「Q2 是卡上必答栏」这件事，不来自任何机制**。
2. **对 run-watch 的膨胀**：**没有任何单问能拦**。真拦截力 = **Q2 的「同形已有几件」× Q4 的净零件记账** 这对组合——前者给出「该并了」的时刻（第 2 件），后者给出「并了没有」的验收数（净行数 / 删除比）。二者缺一：只有计数 ⇒ 知道在膨胀但不知何时该动手（v1 的诊断就是这种状态）；只有同形 ⇒ 判「该并」但无法自证并的效果。
3. **最硬的一条实证**：v1 §4.1 **已经正确诊断过** run-watch 的病因（「无收敛压力」），§4.5 甚至算出了「100 次修复应收敛成 <20 个结构件」；**run-watch 照样长到 38KB 并整体退役**。⇒ **诊断不等于拦截，「设计里写对了」不等于「每件都被问到了」。只有卡上必答的栏目才拦截**。这就是 v3.1 把「同形已有几件」写进 Q2、把「净零件数」写进 Q4 的理由。
4. **对 v3.1 的一处修正（本轮新增）**：v3 §2 把「同形并看」挂在**每周议程**上 ⇒ 按上面的实查节奏，T3→T6 会在**同一周内**全部落地，议程只能收拾残局。v3.1 把并看从「周节奏」提前到「**第 2 件即停手**」（§6.2），依据就是本节的实查节奏（同日内已有 3 件同形）。**这是删议程门没有导致收敛压力丧失的原因**——收敛压力从「时间」换成了「计数」。

### 3.1 方法（结构性 fresh）

## 4. 结论：可以定稿进实施了吗，还差什么

### 4.1 结论

**判定：设计内容已通过验证，但「定稿进实施」还差用户拍板——不建议今晚直接进入实施。**

分三句话说：

1. **判定力通过了回放**：5 个真实缺口的四问回放全部产出了**可执行、可复核、净零件为 0** 的结论（2 修复 / 2 登记 / 1 上游 / 1 已覆盖），且与 v1 记法的「实际发生」形成清晰对照——**差距只在时点，不在判断**；两件历史回放给出了一条更硬的结论：**Q2 能拦 v1 的账本（三命令 30 秒），但没有任何单问能拦 run-watch 的膨胀——拦截力来自「Q2 同形计数 × Q4 净零件记账」这对组合，且必须是卡上必填栏目（v1 §4.1 早有正确诊断，run-watch 照样长到 38KB：诊断不等于拦截，栏目才拦截）**。
2. **红队两路判 `GO-WITH-FIXES`，10 条有效攻击已全部处置**（9 采纳 / 1 明写为局限），且**处置后新增零件仍为 0**。红队同时证伪了「v3.1 只需文字就够了」这一乐观读法：四问的强度上限 = 红队的对抗强度，红队退化则判断质量零机械约束——**这条局限已经写进文档正文（§7.1 残余约束清单），不再藏在对自己的赞美里**。
3. **不能今晚定稿的唯一原因不是设计缺陷，是未拍板项**：11 项待拍板里有 4 项是**关键**（调度链红线收窄 / 部署面算不算域内可逆 / 当班立卡义务+journal 对账 / 红队单点依赖的强度选择），其余 7 项是常规确认。**设计不落地，缺口 1 与缺口 3 就继续每天重复支付兜底成本（今日实查 ≥7 个班次的巡检）**。
